92% of Q2 breaches stem from internal, addressable causes: application bugs (48%) and feed quality issues (44%). Only 8% are external API timeouts beyond direct control.
Action Focus: Defensive coding, schema change alerts, and pre-load validation will directly address the top two categories and reduce breach volume materially in Q3 2026.

Detailed Incidents by Data Source – Q2 2026 (1/2)

DRIFT, MCA, PTS, DSMT-ISG – breach analysis with root cause and resolution

DATA SOURCEROOT CAUSE ANALYSIS (RCA)RESOLUTION / FIXJIRA / INC
Drift (17) Feed Delayed (11): Jobs were triggered before the source Drift system had finished its own data load, resulting in null values or "Not Triggered" statuses.
DB Bug (6): ORA-01400: cannot insert NULL into key fields like "APPLICATIONID" and ORA-12899: value too large for fields like "TECHNICALRECOVERYTIME".		 The timing issue was fixed by moving the IP job schedule to 8:30 AM. The DB bugs require source-side fixes to ensure data integrity. VJ is investigating the "Not Triggered" items. Pending (VJ)
MCA (15) App Bug (15): Multiple failures caused by unexpected timestamp formats from the source and a value for "GAU_OWNER_DELEGATES" that was too large for the database column (4001 vs 4000 chars). A Jira was created to implement a flexible timestamp parser. An INC was raised to trim the oversized attribute, as the field is unused. PRIN-5573
PTS (15) Feed Quality (13): Control-file record count did not match the feed's record count due to multi-line records being counted differently by the source.
DB Bug (2): ORA-12899: value too large error. Incoming data for "INVESTMENT_GROUP" exceeded the max column size (e.g., received 2,741 chars for a 2,500 char limit).		 Feed quality issues were resolved by raising an INC with the PTS source team. The DB bug was also resolved via an INC to have the data trimmed. INC0021438147
INC0023796809
DSMT-ISG (8) App Bug (8): A source-side schema change (attribute changed to nullable) caused a week of ORA-01400: cannot insert NULL errors. Earlier NullPointerException errors also occurred. An INC was raised to the DSMT source team. A permanent code change was released via Jira PRIN-4619 to handle the new nullable attribute. PRIN-4619
INC0023197471

Detailed Incidents by Data Source – Q2 2026 (2/2)

GRC, CRS, Policy, GDW_HRDW – breach analysis with root cause and resolution

DATA SOURCEROOT CAUSE ANALYSIS (RCA)RESOLUTION / FIXJIRA / INC
GRC (4) API Timeout (4): The external API at riskcontrolsproxy.citigroup.net exceeded its 60-second response SLA, causing a "read timeout". All incidents were resolved by manually re-triggering the job, which then completed successfully. This is a recurring external dependency issue. manually retriggered
CRS (2) Internal Process Bug (2): The file pull process failed due to a java.nio.file.AccessDeniedException, indicating insufficient read permissions on the source file. The jobs were manually rerun the next day and completed successfully. This was an internal issue that did not recur. Minimal downstream impact. manually retriggered
Policy (1) API Timeout (1): A "read timeout" occurred when posting to the policy-inventory-metadata-service. The job was manually retriggered and resolved on the same day. This was an isolated incident. manually retriggered
GDW_HRDW (1) Feed Quality (1): The record count in the feed (2,742,409) did not match the count in the control file (2,742,247). The issue self-resolved with the next day's successful run before any action was taken. This was an isolated source-side data quality issue. manually retriggered

Standard Operating Procedure – Dataverse SLA Monitoring

End-to-end workflow from daily monitoring through MCA tester attestation

DAILY MONITORING
Step 1 – MonitorIP Data Ingestion Team monitors dashboard daily for SLA status
Step 2 – AlertSLA breach triggers automatic notification to L2 Support
Step 3 – TicketL2 raises Incident Ticket in ServiceNow assigned to CTI NA EX US CTI GL EX CITI DATAVERSE L3
Step 4 – ResolveL3 investigates and resolves root cause
Step 5 – ReloadJob is re-triggered to reload data
QUARTERLY REVIEW
Step 1 – ReviewControl Owner reviews all SLA breach reports quarterly
Step 2 – Permanent FixFor repeated issues, development team applies permanent fixes
Step 3 – ExportControl Owner exports report and reviews MissedCutoff items
Step 4 – EvidenceReport uploaded as MCA evidence for the quarter
Step 5 – ArchiveDocumentation archived in control repository
MCA TESTER REVIEW
Step 1 – SubmitControl Owner submits attested quarterly snapshot to MCA Tester
Step 2 – ValidateTester validates evidence against control requirements
Step 3 – AttestMCA Tester marks attestation complete upon successful validation
Step 4 – RecordFormal sign-off recorded in MCA system
