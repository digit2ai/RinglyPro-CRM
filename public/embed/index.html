Integración Técnica WordPress → Plataforma

WordPress como System of Record de la identidad del cliente. La plataforma consume esa información mediante una integración segura basada en tokens administrados por WordPress.

Documento de conexión · Cámara cv-105 · Plataforma aiagent.ringlypro.com

Lo que hay que hacer, en una frase: instalar un plugin en WordPress, activarlo, generar un secreto y enviárnoslo. El resto lo hace la plataforma. No hay que programar nada, ni levantar ningún servidor, ni desarrollar el middleware.

1.Arquitectura

  • WordPress es el System of Record (SoR) de la información del cliente.
  • WordPress administra el registro inicial del usuario y mantiene la información maestra del proceso de onboarding.
  • La plataforma consume la información desde WordPress mediante una integración segura y no pide un segundo registro.

La integración es desacoplada: WordPress no depende de la plataforma para operar, y la plataforma no escribe sobre la información maestra. Si la plataforma está caída, el registro en WordPress sigue funcionando y se sincroniza después.

Una sola dirección. Al quedar WordPress como SoR, la plataforma nunca escribe miembros hacia WordPress. Está bloqueado en el código: si alguien intentara activar las dos direcciones a la vez se formaría un bucle de escrituras entre ambos sistemas.

2.Flujo de autenticación

  1. El usuario completa el formulario en WordPress.
  2. WordPress registra la información del cliente como System of Record.
  3. WordPress genera y administra el token de autenticación.
  4. Mediante API o Webhook, WordPress envía el token y la información requerida a la plataforma.
  5. La plataforma valida el token recibido.
  6. Autenticado el usuario, obtiene acceso a la plataforma sin un segundo proceso de registro (Single Sign-On).

3.Lo que tiene que hacer Eduardo

Cuatro pasos dentro de su WordPress. Ninguno requiere tocar código.

Paso 1 — Instalar

Subir el plugin conector

Descargar el archivo del plugin y guardarlo en el servidor como:

wp-content/plugins/camaravirtual-connector/camaravirtual-connector.php

También se puede comprimir esa carpeta en un .zip y subirla desde Plugins → Añadir nuevo → Subir plugin.

Paso 2 — Activar

Plugins → Activar «CamaraVirtual Connector»

Al activarse queda disponible el endpoint de lectura y quedan registrados los avisos automáticos de alta, edición y baja de usuarios.

Paso 3 — Configurar

Ajustes → CamaraVirtual

  • API de CamaraVirtual: https://aiagent.ringlypro.com
  • Slug de la cámara: cv-105
  • Secreto compartido: pulsar Generar secreto nuevo y copiarlo
  • Enviar cambios al instante: dejarlo marcado
Paso 4 — Enviar

Pasarnos tres datos

  1. La dirección exacta del sitio (https://…)
  2. El secreto generado en el paso 3, por un canal privado (no por correo abierto)
  3. Si los miembros están en un plugin de membresías: cuál (MemberPress, Paid Memberships Pro, WooCommerce Memberships) y con qué campos personalizados
Con eso la plataforma queda conectada. Antes de dar de alta a nadie se ejecuta un ensayo que muestra exactamente a quién crearía, sin escribir nada. Solo después de revisar ese listado se aplica.

Comprobación desde su lado (opcional)

Para verificar que el endpoint responde antes de avisarnos, desde una terminal:

SECRETO="pegar-aqui-el-secreto"
SITIO="https://elsitio.com"
TS=$(date +%s)
FIRMA=$(printf "%s" "$TS" | openssl dgst -sha256 -hmac "$SECRETO" | sed 's/.* //')
curl -s -H "X-CV-Timestamp: $TS" -H "X-CV-Signature: $FIRMA" \
  "$SITIO/wp-json/camaravirtual/v1/members?per_page=2"

Debe devolver un JSON con members, total y total_pages. Si devuelve 401, el secreto no coincide o el reloj del servidor está desfasado (la firma caduca a los cinco minutos).

4.Seguridad

  • El token es generado y administrado por WordPress. La plataforma únicamente valida su autenticidad antes de permitir el acceso; no lo emite ni lo almacena.
  • Todas las comunicaciones son HTTPS obligatorio.
  • El token de SSO es de un solo uso, caduca a los cinco minutos y va firmado con HMAC-SHA256. Un token reutilizado se rechaza.
  • El secreto compartido se guarda cifrado en reposo (AES-256-GCM) del lado de la plataforma y nunca se devuelve por API: al consultarlo solo se ve si está configurado y sus últimos cuatro caracteres.
  • WordPress no puede otorgarse permisos dentro de la plataforma. Los campos de privilegio (access_level, governance_role) y de reputación (trust_score, verified) están excluidos de la sincronización por diseño.
  • Ningún registro se borra. Un usuario dado de baja en WordPress pasa a inactive en la plataforma, conservando su autoría de proyectos y mensajes.
Nota sobre el esquema de token. La especificación mencionaba «Bearer Token» para el tráfico entre sistemas. La implementación usa firma HMAC por petición (X-CV-Timestamp + X-CV-Signature) en lugar de un Bearer estático, porque un Bearer capturado sirve indefinidamente mientras que una firma HMAC va atada a la petición y caduca en cinco minutos. El SSO del usuario final sí es un token emitido por WordPress y validado por la plataforma, exactamente como describe la especificación. Si por política se requiere Bearer estático, se puede añadir, pero es un paso atrás en seguridad.

5.Middleware

El microservicio de integración ya está construido y lo opera la plataforma. Eduardo no tiene que desarrollarlo ni alojarlo. Sus responsabilidades:

  • Recibir los eventos desde WordPress.
  • Transformar y normalizar los datos (correos a minúsculas, URLs validadas, nombres deducidos, idiomas de texto a lista).
  • Mapear los campos al modelo de datos de la plataforma.
  • Manejar validaciones y errores: los registros con correo inválido se descartan y se reportan, los duplicados se colapsan, y un registro que falle no interrumpe el resto del lote.
  • Registrar cada ejecución en una auditoría consultable.

La correlación entre ambos sistemas se guarda por ID de usuario de WordPress, no por correo. Así, si un cliente cambia su correo en WordPress, el registro se renombra en la plataforma en lugar de crear un duplicado.

Campos que la plataforma gobierna y WordPress nunca envía

access_level, governance_role, trust_score, verified, verification_level, region_id y los identificadores de pago. Son propiedad de la plataforma y una sincronización jamás los escribe.

Ejemplo de mapeo para un plugin de membresías

Va en el functions.php del tema hijo, no en el plugin, para que no se pierda al actualizar:

add_filter( 'cv_sor_member', function ( $rec, $user ) {
    // Paid Memberships Pro: solo cuenta como miembro quien tiene nivel activo
    if ( function_exists( 'pmpro_getMembershipLevelForUser' ) ) {
        $level = pmpro_getMembershipLevelForUser( $user->ID );
        $rec['active'] = ! empty( $level );
    }
    // Campos personalizados (ACF u otros)
    $rec['company_name'] = get_user_meta( $user->ID, 'empresa', true ) ?: $rec['company_name'];
    $rec['sector']       = get_user_meta( $user->ID, 'rubro',   true ) ?: $rec['sector'];
    return $rec;
}, 10, 2 );

7.Single Sign-On

Para que el usuario pase de WordPress a la plataforma sin volver a registrarse, basta con poner este shortcode en cualquier página de WordPress:

[cv_login label="Entrar a la cámara"]

Se muestra solo a usuarios con sesión iniciada. Al pulsarlo, WordPress emite un token firmado de un solo uso y la plataforma abre la sesión ya autenticada.

Los clientes creados por la integración no tienen contraseña utilizable en la plataforma: entran por este botón. También queda disponible el flujo normal de recuperación de contraseña como alternativa.

8.Objetivo

Implementar una integración desacoplada donde WordPress actúe como System of Record de la identidad e información del cliente, mientras que la plataforma consume dicha información mediante una autenticación segura basada en tokens administrados por WordPress, sin exigir un segundo registro al usuario final.

Archivos de esta integración

  • Plugin conector para WordPress — lo único que se instala
  • Directorio público de miembros — anexo opcional, para mostrar el listado en una web sin mover registros
