The Digit2AI MCP Server

One orchestrator. Seventy-five typed tools. Eight autonomous agents. Every channel — voice, web, portal, admin, and external machine callers — enters through the same gateway, and no channel holds a private copy of business logic. This document describes the server, its endpoints, the federated modules behind it, how data moves between those modules, and how referential consistency is guaranteed rather than assumed.

The architectural claim

A tool is defined once, in one file, with one JSON Schema, one authorization contract, and one database write path. The phone agent, the web orb, the customer portal, the admin console and an external MCP client all invoke that same function object. There is no second implementation of "book an appointment" and therefore no way for two channels to disagree about what an appointment is.

What a CTO should take away in ninety seconds

  • The gateway is the policy enforcement point. Authorization, tenancy, budget and audit are applied in callTool(), in code — not in a system prompt an LLM can be argued out of.
  • Tenancy is injected, never accepted. tenant_id is deleted from every incoming argument object and re-supplied from the authenticated session. A model literally cannot address another tenant's data.
  • Modules share a schema, not an integration. Cross-module consistency is a foreign-key property of one relational store, not an ETL job that can lag or drift.
  • Every call is audited. Tool, channel, actor, redacted arguments, success, latency and cost land in an append-only relation on every invocation, including denied ones.
  • The system is interoperable outward. A published A2A Agent Card plus a JSON-RPC 2.0 MCP endpoint lets third-party agents discover and call capabilities without bespoke integration work.

02Why one brain and not eight services

The conventional shape for this problem is one microservice (or one vendor agent) per function: a booking bot, a billing bot, a dispatch bot. That shape fails in a specific, predictable way.

Per-channel agents (rejected)

  • Booking logic exists in the phone agent, the web widget and the portal — three implementations, three drift vectors.
  • Authorization lives in prompts. Prompt injection becomes privilege escalation.
  • Each agent holds its own view of the customer. Reconciliation becomes a permanent engineering tax.
  • An availability change ships three times, or ships twice and silently double-books.
  • No single place to answer "what did the AI do today, and what did it cost".

One Brain, many channels (built)

  • dispatcher.check_availability is the only source of availability in the entire system. Every channel reads it.
  • Authorization is a property of the tool descriptor, evaluated by the gateway before the handler runs.
  • All channels resolve to the same customer_id in the same relation.
  • A pricing change is one file. Every surface reflects it on the next call.
  • One audit relation answers every operational, security and finance question.

Design rule enforced in code

Prompts describe intent. Prompts never describe permission. Any control that matters — who may call a tool, from which channel, on whose data, within what budget, and whether a human must sign off — is a field on the tool descriptor evaluated by the gateway. A jailbroken model reaching the gateway is indistinguishable from an honest one: it hits the same five checks and fails the same way.

03System topology

Three planes. The orchestration plane decomposes work and dispatches long-running analytical agents. The execution plane is the MCP gateway that fronts the typed tool registry. The data plane is a single relational store partitioned by namespace prefix and tenant key.

The one detail that breaks agents when it is missed

listTools() computes effective trust exactly the way callTool() does. If a live session omits identity_verified, every identified-trust tool is filtered out of the catalog and the agent is handed a toolset it cannot do its job with.

The observable symptom is a Receptionist that takes a message instead of quoting — it has no estimator.price_quote in its catalog, so it improvises. The fix is not prompt engineering; it is passing the flag.

06Authorization model

Five orthogonal checks, evaluated in order, all in the gateway. A tool descriptor declares its requirements; the gateway evaluates them. Neither the model nor the channel participates in the decision.

6.1 — The channel trust ladder

Channels map to a base trust level. Trust is a total order, and comparison is index-based.

Fig. 2 — Trust ladder. A channel's base level is fixed; only supplied identity promotes public_web to identified.
const CHANNEL_TRUST = {
  web_orb: 'public_web',  web_chat: 'public_web',
  phone:   'phone',       portal:   'customer',
  admin:   'staff',       system:   'staff'
};
const TRUST_ORDER = ['public_web', 'identified', 'phone', 'customer', 'staff'];
function trustAtLeast(actual, required) {
  return TRUST_ORDER.indexOf(actual) >= TRUST_ORDER.indexOf(required);
}

6.3 — Tenant injection

This is the single most important line in the codebase from a data-security standpoint.

// Tenant is ALWAYS injected from session context — a model cannot supply it.
const safeArgs = { ...args };
delete safeArgs.tenant_id;
// ...
const result = await tool.handler(safeArgs, { ...context, tenant_id });

Every handler receives ctx.tenant_id from the authenticated session and every query filters on it. An LLM that emits {"tenant_id": 47} in its tool arguments has that key deleted before the handler sees it. Cross-tenant access is not defended against at the query layer as a matter of discipline — it is made unrepresentable at the gateway. The integration suite asserts this across the entire registry, not on a sampled subset.

6.4 — Human-in-the-loop

Two tools carry requires_approval. When one is called, the gateway writes an approval row with redacted arguments and returns before the handler runs. The tool never executed; nothing is pending in a queue that might fire later on its own.

  • bookkeeper.issue_refund — money leaving the business always gets a human.
  • payroll.submit_pay_run — and additionally requires an approved run and a connected licensed provider. filed status can only be set from a real provider response; with no provider every run is draft-only and every surface says so.

Release happens via executeApproval(), which re-reads the stored arguments and executes with an explicit admin context and the approving user recorded. A rejected approval transitions to rejected and can never execute. Redaction on the stored arguments is regex-based over password|card|cvv|token|secret|gate_code|ssn, and long strings are truncated at 400 characters — the approval queue is a human surface and must not become a secrets store.

07Request lifecycle

The complete path of one tool call, from HTTP to audit row. Every branch that returns early still writes an audit record — denials are as observable as successes.

  1. Transport. POST /mcp/tools/call with {tool, arguments, context}, over a session cookie or an x-mcp-key header.
  2. Caller resolution. resolveContext() derives {tenant_id, channel, role, actor, user_id} by precedence. No resolution → 401, and no tool executes.
  3. Registry lookup. REGISTRY[toolName]. Unknown tool → audited failure. A missing tenant is treated identically — there is no anonymous execution mode.
  4. Global enablement. If the agent is switched off platform-wide, fail with a message naming the agent rather than a generic error.
  5. Per-tenant enablement. Cached plan lookup (60 s TTL, explicitly bustable on plan change). Not enabled → employee_not_enabled.
  6. Effective trust. Base level from the channel, promoted to identified only when identity_verified is set. Computed identically here and in listTools() so discovery and execution cannot disagree.
  7. Authorization. Channel allow-list, then minimum trust, then role allow-list. Each denial carries a distinct code and a message that states what was required and what the session actually had.
  8. Budget. Sum today's cost_cents for the tenant against the cap. Over budget on a non-admin channel → degrade to typed self-service, explicitly.
  9. Argument sanitization. tenant_id deleted from the argument object. Session tenancy is merged into the handler context.
  10. Approval interception. If requires_approval, write the approval row, audit, and return {requires_approval:true, approval_id}. The handler does not run.
  11. Execution. tool.handler(safeArgs, {...context, tenant_id}). Handlers own their own transactional boundaries; multi-row writes commit atomically or not at all.
  12. Audit. Tool, employee, channel, actor, redacted arguments, success, error, latency and cost persist to the append-only call log. Wrapped in its own try/catch: auditing must never break the call it is auditing.
  13. Response. Structured result. Authorization denials map to HTTP 403; everything else returns 200 with success:false, so clients distinguish "you may not" from "it did not work".

Why exceptions never escape

The handler call is wrapped; a thrown error becomes an audited {success:false, error}. A conversational agent receiving a structured failure can explain it to a caller and offer an alternative. An agent receiving an unhandled exception produces a dead air gap on a live phone call. The contract is chosen for the channel with the least tolerance for ambiguity.

Queue semantics

  • Exactly-once dispatch. The worker selects pending rows FOR UPDATE inside a transaction and flips status to processing before releasing the lock. Concurrent workers cannot double-run a task.
  • Result columns are separated by purpose. Markdown output, structured JSON and generated artifacts live in distinct columns, so re-running a task with a different agent cannot erase a prior agent's artifacts.
  • Status overrides are allow-listed. An agent may only return ready_for_review or out_of_scope; anything else normalizes. A model cannot invent a workflow state.
  • Cost and model are recorded per task. agent_model and agent_cost_usd persist on the row, so spend is attributable to a specific piece of work rather than a monthly aggregate.
  • Failure is a state, not a crash. A thrown error becomes agent_status='failed' with the message truncated to 2000 characters. The task is re-runnable.
  • Missing context is returned, not fabricated. When a request is too vague to analyze, agents return a missing_context list instead of a confident-sounding but ungrounded output.

Degradation without credentials

With no model API key configured, analytical agents fall back to a labelled heuristic path and flag results is_simulated: true. The system continues to function end to end, and every consumer — UI, API, export — can distinguish a real inference from a heuristic. It never silently substitutes one for the other.

10Data management — the canonical model

The consistency question — "is the customer the Dispatcher sees the same customer the Bookkeeper bills?" — is answered structurally. There is one customer relation. Every agent reads and writes it. Consistency is a foreign-key property, not a synchronization process.

10.1 — The entity spine

Five identifiers thread the entire operational lifecycle. Every agent that participates in a job joins on one of them. There is no per-agent identifier space and therefore no mapping table to fall out of date.

Fig. 3 — The entity spine and its fan-out. appointment_id is the join key every agent shares.

clients is the tenant registry for the whole platform: it carries the inbound voice number, the outbound messaging number and the owner escalation number. A dialed phone number resolves to a clients.id, and that identifier is what the voice brain, the booking tool bus, the message feed and the command centre all key on. One inbound call therefore reaches the correct tenant's calendar without any module having to know how the call arrived.

The rule this table encodes

12Data transfer patterns

Five transfer mechanisms, each chosen for a specific latency and durability profile. Notably, the dominant intra-module pattern is not a network call.

#PatternMechanismUsed forFailure mode
1Shared relation

2In-process registry call A handler calls another tool through the same callTool() gateway, inheriting the full authorization and audit chain. 5Streaming WebSocket for live call audio and turn events; server-sent events for live bid and status feeds. Real-time conversation; live auction state. Disconnect terminates the session cleanly; durable state was already committed on each turn, not buffered until the end.

13Consistency proof — the costing walkthrough

The strongest demonstration that cross-module data is genuinely the same data is a function that reads from five agents at once and reconciles to the penny. controller.job_costing is that function. It is worth reading closely, because it also demonstrates the system's honesty contract. 

// For each completed service record in the period…
for (const r of records) {

  // ① CREW MANAGER's data — real clocked minutes, joined on appointment_id
  const entries = await TimeEntry.findAll({
    where: { tenant_id: ctx.tenant_id, appointment_id: r.appointment_id }
  });
  if (!entries.length) { missingHours++; continue; }   // ← EXCLUDED, not estimated

  const labor_minutes = entries.reduce((a, t) => a + (t.minutes || 0), 0);
  const labor_cents   = entries.reduce((a, t) =>
    a + Math.round(((t.minutes || 0) / 60) * (rateById[t.employee_id] || 0)), 0);

  // ② DISPATCHER's data — the route this job sat on, drive cost amortized per stop
  const route = await Route.findOne({
    where: { tenant_id: ctx.tenant_id, service_date: r.service_date, crew_id: r.crew_id }
  });
  const drive_minutes = (route?.drive_minutes && route.stop_count)
    ? Math.round(route.drive_minutes / route.stop_count) : 0;

  // ③ BOOKKEEPER's data — materials booked against the same appointment
  const expenses = await Expense.findAll({
    where: { tenant_id: ctx.tenant_id, appointment_id: r.appointment_id }
  });

  // ④ CREW MANAGER's revenue figure from the service record itself
  const revenue_cents = r.charges_cents || 0;

  // ⑤ CONTROLLER derives and persists — its own relation, nobody else's
  const margin_cents = revenue_cents - (labor_cents + drive_cents + material_cents + overhead_cents);
}

What this proves about consistency

  • Four agents' write products are joined on one key: appointment_id.
  • No agent needed an API contract with another. The schema is the contract.
  • Every row in the join is filtered by tenant_id supplied by the gateway, so a costing report cannot leak across tenants even in an aggregate.
  • Labour cost is minutes × pay_rate from the actual employee record — not the scheduled duration, not an average.
  • Persisting is opt-in (recompute) and destructive-then-recreate per appointment, so the derived table can never accumulate duplicate rows for one job.

The honesty contract

The continue on line 8 is the most important line in the function. A completed job with no clocked hours is skipped and counted, and the result carries the gap forward explicitly: 

data_gap: `${missingHours} completed job(s) have no
clocked hours, so they are excluded rather
than estimated. Have crews clock in and out
to close this gap.`

A system that silently interpolated the missing hours would return a smooth, plausible, wrong margin. The design choice here — report the gap, name the cause, state the remedy — is applied consistently: the Controller's savings figures trace to real rows or are omitted, and compensation is shown only where the source actually states it.

14Isolation and tenancy

Four independent layers. Any one of them failing does not by itself produce a cross-tenant read.

LayerMechanismFailure containment
1 · ResolutionTenant derived from URL slug, dialed number, or authenticated session — never from a request body or a model argument. An unknown slug returns 404 rather than falling back to a default tenant.A wrong resolution yields "not found", not another tenant's data.
2 · Injectiondelete safeArgs.tenant_id at the gateway; session tenancy merged into handler context.Model-supplied tenancy is structurally discarded.
3 · QueryEvery handler filters on ctx.tenant_id. Asserted across the entire tool registry by the integration suite, not on a sample.A missing filter is caught before merge, not in production.
4 · NamespacePer-module table prefix. A module's queries cannot accidentally address another module's relations.Blast radius of a bad migration is one prefix.

Privilege boundaries encoded in code

Several controls exist specifically because a prompt cannot be trusted to hold them. Each is a code path, and each has a regression test.

  • Federated identity systems cannot grant local privilege. A synchronizing external directory may write name, company, contact and profile fields. It may not write access level, governance role, trust score or verification state. Widening that allow-list is a privilege-escalation change, not a feature.
  • And the reverse. Records pushed outward carry no role or capability. The receiving system decides its own defaults. Neither side can escalate in the other.
  • Directional sync is exclusive. Pull and push cannot both be enabled — running both is an echo loop, so each endpoint refuses in the opposite mode and the companion plugin suppresses its own outbound event while applying an inbound write.
  • Deletes are soft. A record absent upstream is deactivated, never dropped, because it authors messages, tickets and financial history. Administrators and the account owner are skipped even when deactivation is enabled — a bad sync cannot lock out whoever must fix it.
  • Super-admin sees counts and money, not customer PII. Reaching customer records requires audited impersonation with a written reason, recorded in its own relation.
  • Public projections delete, not blank. A field marked private is removed from the object before it reaches any public surface — JSON export, agent card and every tool response — rather than being hidden by a client.
  • No card data at rest. The processor holds instruments; the system stores identifiers, brand, last four and expiry.

15A2A — the agent-to-agent surface

MCP handles our agents calling our tools. A2A handles somebody else's agent discovering and calling our capabilities without a bespoke integration. Both are implemented; the A2A surface is live and public.

Discovery

GET /.well-known/agent.json — a standards-located A2A Agent Card. A foreign agent finds it by convention, with no registry and no onboarding.

Invocation

POST /api/agent/:slug/mcp — canonical MCP over JSON-RPC 2.0. initialize, ping, tools/list, tools/call, with notifications/* accepted and acknowledged 202.

Fallback

Plain REST mirrors of every skill for clients that do not speak JSON-RPC: /card, /profile, /resume, POST /match, POST /message.

Why this surface is safe to expose publicly

  • One privacy projection, applied before anything is served. A single function filters the record; the card, the JSON export, every REST read and every MCP tool response go through it. There is no path that reaches around it to the raw record.
  • Write capability is deliberately minimal. The only mutating skill appends to a private inbox. It sends no reply, triggers no automation, and exposes no read-back.
  • Rate limits are per IP and per tool. The two expensive skills — inference-backed matching and the write path — carry independent budgets.
  • Card and engine cannot drift. Advertised targets are read from the same settings record the matching engine uses, so the card cannot claim a target the engine does not score against.
  • Honest positioning. No recruiting product discovers candidates via MCP today. This is a positional bet on the interoperability standard, documented as such rather than sold as a traffic channel.

Configuration principles

  • Absent credentials degrade, never crash. No inference key yields a labelled heuristic. No payroll provider yields draft-only runs. No mapping key yields a keyless geocoder and a scaled diagram. The system boots and functions in every case.
  • Every fallback is labelled in the payload. is_simulated, enriched_by, source: 'heuristic'. A consumer can always distinguish a real result from a degraded one.
  • Behaviour toggles live in configuration, state lives in the database. Run-state is queryable at an endpoint, not hidden in an environment variable.
  • Secrets at rest are AES-256-GCM encrypted under a derived key and returned to any UI as {set, hint} — never as plaintext. Re-saving with an empty field preserves the stored value.

Because every capability invocation crosses one gateway, the audit relation is a complete record. This is the operational payoff of the single-brain design.

Derived operational views

  • Per-agent activity. Calls, failures, cost, mean latency and a ranked tool-usage histogram per agent over a window — the AI staff screen an operator actually looks at.
  • Pending approval count surfaced alongside activity, so a blocked queue is visible rather than discovered later.
  • Recent call tail for live debugging without a log search.
  • Measured cost per tenant reconciled against modelled assumptions, so unit-economics estimates are corrected by evidence rather than carried forward.

Cost as a first-class control, not a monthly surprise

The daily cap is evaluated before execution, per tenant, from the same audit relation that records spend. Exceeding it degrades that tenant to typed self-service with an explicit message — the product keeps working. The admin channel is exempt so an operator is never locked out of the system by its own budget guard.

Add a tool

One key on an existing agent's tools object:

my_tool: {
  description: '…',
  min_trust: 'identified',
  channels: ['phone', 'admin'],
  roles: ['owner'],

  handler: async (args, ctx) => { … }

It is now discoverable, authorized, tenant-scoped, budgeted and audited on every channel. No route, no middleware, no client change.

Add an agent

One module exporting {id, name, role, replaces, channels, supervisor_role, tools}, added to the EMPLOYEES array. The registry flattens it at boot; the roster endpoint, the tool catalog, the activity view and the plan-enablement check all pick it up with no further edits.

Add a module

A self-contained Express Router with its own Sequelize instance, its own table prefix, and a /tools/list + /tools/call pair. Mount it in one line. Any existing MCP client can call it immediately — the contract is already uniform.

Invariants a contributor must not break

  • Authorization is never expressed in a prompt. It is a field on the tool descriptor.
  • tenant_id is never read from tool arguments. It is deleted and re-injected.
  • No channel gets a private copy of business logic. If two surfaces need the same behaviour, they call the same tool.
  • Every derived figure traces to a real row or is omitted with the gap named. Never interpolate to make a report look complete.
  • A degraded path is labelled in the payload, not only in a log line.
  • Audit failure never propagates to the call being audited.
  • Soft-delete anything that authors history. Hard deletes destroy the audit trail that makes the rest of this document true.

Summary for the CTO

The system is a single policy enforcement point in front of a flat registry of seventy-five typed capabilities, grouped into eight autonomous agents, backed by one relational store partitioned by namespace and tenant.

Cross-module data consistency is not maintained — it is structurally impossible to violate. There is one customer relation, one appointment relation, one invoice relation. Agents hand work to each other by writing a foreign key, not by calling an API or emitting an event that might not arrive. The Controller's margin figure and the Bookkeeper's invoice are computed from the same row, which is why they always agree.

The controls that matter to an auditor — tenancy, authorization, human sign-off on money movement, complete call-level audit, bounded spend — are enforced in code at the gateway, not requested of a language model in a prompt. That is the difference between a system that behaves correctly and one that behaves correctly until someone types the right sentence into it.
