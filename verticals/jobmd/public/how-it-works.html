How JobMD.io works

JobMD.io is an AI Healthcare Talent Intelligence Network for recruiting surgeons, doctors and medical staff. This page explains what runs underneath: the eleven agents behind the MCP orchestration layer, how a candidate moves from prospect to placement, and the two architecture APIs that generate the platform’s own build documents.

1. What the platform does

Three groups of people meet here. Surgeons, doctors and medical staff looking for the right role. Hospitals, health systems and IDNs looking for the right person. And JobMD.io Recruiters, who run the process with AI assistance rather than being replaced by it. Platform Administrators manage clients, candidates, recruiters, placements, agents and workflows.

Two persistent records carry everything. The Talent Intelligence Record holds twenty-five fields per candidate — specialty and subspecialty, education, residency, fellowship, board certifications, licenses, procedure expertise, robotic platforms, preferences, availability, recruitment status and match history. The Hospital / Client Intelligence Profile holds nineteen — organisation, facilities, open positions, requirements, robotics platform, compensation range, call schedule, employment model, recruiting priorities and pipeline.

Fifteen surgical specialties are configured at launch, and the taxonomy is stored as data with a subspecialty relation, so adding a specialty or a staff role is data entry rather than a redesign.

2. The eleven agents and the MCP layer

A central MCP orchestration layer coordinates eleven specialised agents. Each performs one recruitment function and can hand work to the others through agent-to-agent workflows. The layer injects the tenant from the session, enforces role and channel authorisation before any tool call, and audits every call — including the ones it denies.

3. How a match is produced

Seven dimensions are evaluated at once, not in sequence: Clinical, Technology, Geographic, Career, Compensation, Availability, and Cultural / Professional.

Every match returns three things together, and the third is the one that matters: a score, a plain-language explanation of why the candidate was selected, and the material gaps. A score with no gaps attached is a number nobody can act on.

4. The recruitment pipeline, and who may move a candidate

Thirteen stages, in order: Prospect → Contacted → Interested → Qualified → Matched → Submitted → Hospital Review → Interview → Offer → Negotiation → Accepted → Credentialing → Placement.

Recruiters and Platform Administrators can advance any stage. Agents can advance only four, and only where a named agent function actually produces that state:

StageAgent permitted to set it
Contacted, InterestedRecruitment Outreach Agent
QualifiedClinical Qualification Agent
MatchedCandidate Matching Agent
InterviewScheduling Agent
Prospect, Submitted, Hospital Review, Offer, Negotiation, Accepted, Credentialing, PlacementNone. People only.
Why the list is short. The project request authorises agent updates only in general terms — it never says which agent may set which stage. Rather than guess, authority was granted only where a named agent function produces the state, and the ambiguity is recorded as an open question. No agent can move a candidate to Offer or Placement.

5. The architecture API

Two agents generate JobMD.io’s own build documents from the project request. They answer different questions and return different shapes, and both read one shared transcription of the request, so they can never disagree about how many pipeline stages exist.

The two read endpoints persist nothing and contain no personal data by construction, which is why they are open. Everything that writes, or that reads stored rows, requires a session.

# A build plan, deterministic path
curl -s "https://aiagent.ringlypro.com/jobmd/api/v1/architect/plan?model=0"

# An architecture record, and just its open questions
curl -s "https://aiagent.ringlypro.com/jobmd/api/v1/spec" \
  | python3 -c "import sys,json; [print(q['blocksBuild'], q['topic']) for q in json.load(sys.stdin)['record']['openQuestions']]"

Every response carries its own provenance: composed_by (model or deterministic), is_simulated, the model id or null, and the full verification result. It also reports what the model actually did — model_rewrites_parsed and model_rewrites_accepted — so a model that answered but changed nothing can never be mistaken for one that had nothing to add.

6. The rules enforced in code

These are not instructions given to a model. They are checks that run on every document before it is returned, and a document that fails any of them is refused rather than shipped.

  • The model never writes a named entity. The specialties, agents, stages, dimensions and profile fields are held in code and read verbatim, in order. The model is offered only a prose rewrite, and each rewrite is discarded unless the whole document still verifies.
  • The structure is identical with or without an API key. Only wording changes, and the response says which path produced it.
  • Nothing is invented. A component that is not in the registry, a discovery source the request never named, an MCP endpoint path that appears nowhere — all rejected. Where a value is unknown it is left empty and recorded as an open question.
  • Nouns are preserved. Talent Intelligence Record, Robotics Division, IDNs, JobMD.io Recruiters and the agent names must survive verbatim.
  • No candidate data reaches these documents. Field names are architecture; values are not. Anything shaped like an email, phone number, licence, NPI or DEA number is refused.
  • The generators cannot reach the database. They import no model and no connection, and contain no write call — so “never execute, deploy or migrate” holds by reach, not by promise.
  • Nothing may be dropped or reordered. Fifteen specialties, eleven agents, thirteen stages, seven dimensions, twenty-five and nineteen profile fields — checked as exact ordered lists, because a document missing one stage still looks correct.
How this is proved. The test suite does not check the happy path. It builds valid documents, deliberately breaks them — drops a stage, invents a component, grants an agent authority over Placement, leaks a licence number, hides the truncation — and fails unless every one is refused.

7. What is not built yet

The platform documents are generated and verified. The recruitment platform itself is specified, not shipped. Stated plainly so nobody reads a build plan as a running system:

  • There is no physician database yet. The project request cites one as a discovery source; it does not exist here, and the architecture record flags that as blocking.
  • No MCP endpoint paths exist. Neither the request nor the registry names one, so the record leaves the list empty rather than filling it in.
  • Section 10 of the request is truncated mid-sentence, so Automated Talent Discovery lists only the two sources the text actually states.
  • The eleven agents, the matching engine and the pipeline are specified in the documents — they are not yet running services.
